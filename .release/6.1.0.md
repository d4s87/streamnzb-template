# DraCuLa StreamNZB Template 6.1.0

6.1.0 improves DraCuLa's release-preparation and validation process. It does not change filtering, scoring, trusted-tier policy, adaptive filtering, profile content, Define Library behavior, or formatter behavior. Compatibility remains StreamNZB 6.1.0 / Jhin 0.7.1, unchanged from 6.0.1.

## Release automation

This release adds a deterministic release-validation foundation and an automated release-preparation workflow:

- Release version and provenance validation, run against the actual repository and GitHub state before any preparation happens.
- Automated README, CHANGELOG, and release-note preparation, generated from the current repository rather than hand-edited.
- Release-impact accounting: the set of merged pull requests since the previous stable release is inspected and checked against the requested version bump.
- Compatibility and profile/Define count snapshots, captured and validated against the live repository.
- Tag and published-release collision checks, so preparation fails closed if a conflicting tag or release already exists.
- Stale-`main` detection, so a release-preparation pull request fails closed if `main` advances underneath it.
- Release-preparation pull requests are opened automatically once validation passes.

Preparation is automated; curating the public release note and reviewing/merging the resulting pull request remain manual, human-reviewed steps. Publishing a release (tagging and creating the GitHub release) is a separate, manually gated step that is not yet implemented.

## Validation and safety

- The exact commit release housekeeping was generated from (`prepared_from_sha`) is recorded and re-checked; a generated preparation pull request fails closed if `main` moves on before it merges.
- The requested version is checked against release-impact evidence collected from the actual merged pull requests in range — an under-classified version request is rejected, not silently accepted.
- Tag and published-release collisions fail closed rather than silently overwriting or proceeding.
- The credential used to open and update a release-preparation pull request is narrowly scoped to only what that step needs.
- Ordinary pull request validation continues to run without any elevated credential.
- Release Drafter's draft inventory is treated as informational only during preparation; when it cannot be reliably read, that limitation is reported explicitly rather than the check falsely claiming no drafts exist.
